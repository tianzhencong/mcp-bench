# Thinking vs No-Thinking 模型在 Retail Agent 评测中的差异分析报告

## 1. 总体结论

| 指标 | Thinking 模型 | No-Thinking 模型 | 差距 |
|---|---|---|---|
| 平均 Reward | **0.770** | 0.680 | +13.2% |
| 完美完成率 | **77.0%** (351/456) | 68.0% (310/456) | +9.0% |
| 完全失败率 | 23.0% (105/456) | **32.0%** (146/456) | -9.0% |
| DB 正确率 | **0.796** | 0.722 | +10.2% |
| 沟通正确率 | **0.956** | 0.930 | +2.8% |

Thinking 模型在 114 个任务中：
- **47 个任务表现更好**（其中 17 个大幅领先 ≥0.5）
- 47 个任务持平
- 20 个任务略逊（其中仅 3 个大幅落后）

**核心发现：差距主要来自 DB 维度（工具调用后数据库状态是否正确），而非沟通维度。** 也就是说，No-Thinking 模型能正确理解用户意图并沟通，但在执行工具调用时更容易传错参数。

## 2. 17 个 Thinking 大幅领先的 Case 逐一分析

### Case 1: Task 3 — T-shirt 选项查询 + 修改订单
**Thinking 0.75 vs No-Thinking 0.00**

**场景**：用户 Yusuf 想知道商店里有多少种 T-shirt，然后把他所有待发订单中的小号 T-shirt 换成紫色聚酯纤维的。涉及 12 步操作：查用户 → 查 2 种产品详情 → 查 5 个订单 → 找到有 T-shirt 的待发订单 → 修改。

**No-Thinking 出错点**：DB 操作全部正确（DB=1.0），但 **COMMUNICATE=0.0** — 没有正确告知用户 T-shirt 有多少种选项（期望回答 "10"）。模型做对了所有工具调用，却在总结信息给用户时遗漏了关键数字。

**Thinking 为什么做对了**：Thinking 模型在内部推理时明确记录了"需要数清楚可用变体数量并告知用户"，No-Thinking 模型处理了复杂的订单修改流程后，忘记了用户最初的简单问题。

**错误类型**：**多任务记忆丢失** — 同时处理"查询"和"修改"两个请求时，完成了复杂的修改但忘了简单的查询。

### Case 2: Task 20 — 中彩票升级全部商品到最贵
**Thinking 0.75 vs No-Thinking 0.00**

**场景**：用户 Ethan 中了彩票，想把一个订单里所有 4 件商品都升级到最贵的变体（水壶、台灯、鞋子、运动背包），鞋子要保持同尺码。用 Gift Card 支付差价。

**No-Thinking 出错点**：所有查询步骤都正确，但最终的 `modify_pending_order_items` **action_match=False** — 虽然调用了正确的 API，但传入的 `new_item_ids` 或 `payment_method_id` 有误。同时泄露了内部 prompt 内容（`effort: medium`）。

**Thinking 为什么做对了**：需要同时比较 4 个产品的所有变体价格，找出每个的最贵选项，还要确保鞋子尺码不变。Thinking 模型在推理阶段逐一核对了每个产品的变体价格后才构造参数。

**错误类型**：**多变量精确选择** — 需要同时处理 4 件商品 × 多个变体的价格比较，选出正确的 item_id 组合。

### Case 3: Task 99 — 换自行车 + 拼图 + 相机（跨订单多操作）
**Thinking 1.00 vs No-Thinking 0.25**

**场景**：Sofia 有 3 个需求跨 2 个订单：①换自行车到大车架；②同一订单里的拼图换成多 1000 片的（偏好艺术主题）；③另一个订单里的相机换成低分辨率的；④取消某订单里的滑板。需要同时提出自行车和拼图的需求。

**No-Thinking 出错点**：第一个订单的换货（自行车+相机）成功，但第二个订单的换货（拼图+自行车在同一订单里，且用户要求同时提出）**action_match=False**。在 4 次试验中只成功 1 次（0.25），说明不稳定。

**Thinking 为什么做对了**：4 次试验全部成功（1.0）。Thinking 模型能可靠地处理"同一订单里换两件不同商品"的批量操作，正确构造包含多个 item_id 的数组参数。

**错误类型**：**批量操作参数构造** — 一次 exchange 调用里要传两个 item_id + 对应的两个 new_item_id，No-Thinking 容易漏掉或搞错配对。

### Case 4: Task 101 — 跨订单改地址 + 换手表 + 换净化器
**Thinking 0.75 vs No-Thinking 0.00**

**场景**：Noah 有两个订单需要处理：①手表订单改地址（用另一个订单上的纽约地址，不想手动输入）+ 换硅胶表带为金属；②净化器订单换成大号夜灯模式。涉及 3 次修改 API 调用。

**No-Thinking 出错点**：3 个操作中 2 个 action_match=False。关键问题：
1. `modify_pending_order_address` 失败 — 可能是地址字段（从另一个订单提取）有细微差异
2. `modify_pending_order_items`（手表）失败 — item_id 选错
3. 对话中泄露了 `effort: medium` 和 `<tool_call>` 标签

**Thinking 为什么做对了**：3 个操作全部正确。在需要"从订单 A 提取地址应用到订单 B"这种跨订单信息传递场景中，Thinking 模型在推理阶段明确追踪了两个订单的地址，No-Thinking 模型更容易搞混。

**错误类型**：**跨订单信息传递** + **格式控制失败**（泄露内部 prompt）

### Case 5: Task 2 — 查 T-shirt 选项 + 退三件商品
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Yusuf 想知道 T-shirt 有多少种选项，同时退三件商品（清洁器、耳机、智能手表）。

**No-Thinking 出错点**：和 Task 3 类似 — DB=1.0（退货操作正确），但 COMMUNICATE=0.0（没有正确告知 T-shirt 选项数量 "10"）。`return_delivered_order_items` 的 action_match 也为 False。

**错误类型**：**信息汇总遗漏** + **退货参数错误**

### Case 6: Task 7 — 换水壶 + 台灯（条件分支）
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Mei 想换水壶（换大的）和台灯（换暗的，偏好 AC > 电池 > USB）。**但如果 agent 要求确认，就只换台灯不换水壶。**

**No-Thinking 出错点**：`exchange_delivered_order_items` 的 action_match=False。关键在于这个条件分支 — 用户一开始说换两件，但确认时反悔只换一件。No-Thinking 模型没有正确处理这个意图变更。

**Thinking 为什么做对了**：Thinking 模型在推理阶段明确标记了"用户说确认时只换台灯"这个条件，在构造最终的 exchange 调用时只包含了台灯的 item_id。

**错误类型**：**条件分支处理** — 用户改变主意时，需要回溯修正之前计划的操作。

### Case 7: Task 19 — 退水壶 + 换最便宜版本（需计算比较）
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Mei 想退水壶、换宠物床和办公椅为最便宜版本。如果只能做一件，选省钱最多的。需要告知两种选项分别省多少（期望 54.04 和 41.64）。

**No-Thinking 出错点**：DB=1.0 但 COMMUNICATE=0.0 — 退货操作成功了，但没有正确计算和告知两种方案的省钱金额。

**Thinking 为什么做对了**：Thinking 模型在推理中逐步计算了价格差异，最终正确报告了两个金额。

**错误类型**：**数值推理** — 需要从产品变体中找到最便宜的，计算价差，并正确传达给用户。

### Case 8: Task 23 — 换头盔 + 行李箱 + 改烤架（3 个订单 3 种操作）
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Sofia 需要 3 种操作跨 3 个不同订单：①换头盔（delivered 订单）；②换行李箱（另一个 delivered 订单）；③改烤架（pending 订单，改成和已收到的那个一样的型号）。涉及 12 步操作。

**No-Thinking 出错点**：**所有 12 个 action_check 全部失败**。根本原因：`find_user_id_by_name_zip` 失败了 — 模型没能正确调用用户身份验证，导致后续所有操作都无法进行。agent 回复 "I'm sorry, but I couldn't find a user account matching that name and zip code"。

**Thinking 为什么做对了**：同样的用户名和 zip code，Thinking 模型成功调用了 `find_user_id_by_name_zip` 并完成了全部 12 步操作。

**错误类型**：**基础身份验证失败** — No-Thinking 模型在构造 `find_user_id_by_name_zip` 参数时可能搞错了大小写或格式，导致整个会话崩溃。

### Case 9: Task 28 — 退 5 件商品 + 取消水管 + 计算退款总额
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Isabella 想从已收到的订单里退 5 件商品（分布在 3 个订单中），还想取消一个 pending 订单中的水管（如果不能部分取消就算了）。最后需要计算退款总额（期望 918.43）。

**No-Thinking 出错点**：退货操作全部成功，但 `calculate({"expression": "200.8 + 96.35 + 193.38 + 231.37 + 196.53"})` 的 action_match=False，且 COMMUNICATE=0.0 — 没有正确计算并告知退款总额。

**Thinking 为什么做对了**：正确使用了 calculate 工具计算出 918.43 并告知用户。

**错误类型**：**数值计算** — No-Thinking 模型可能在心算或调用 calculate 工具时传入了错误的表达式。

### Case 10: Task 47 — 退净化器和吸尘器（用户故意给错订单号）
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Daiki 想退空气净化器和吸尘器。**故意先给错订单号 9502126**，被纠正后给 9502127，再被纠正后补上 W 前缀变成 #W9502127。退完后还要算剩余商品总价（期望 1095.55 和 1528.14）。

**No-Thinking 出错点**：退货本身有问题（action_match=False），calculate 调用也失败。但 COMMUNICATE=1.0 说明金额告知正确 — 可能是用心算而非工具得出的。

**错误类型**：**错误恢复** — 处理用户多次给错信息的场景，需要逐步纠正，No-Thinking 模型在这种"多次重试"场景中更容易混乱。

### Case 11: Task 57 — 查到货时间，未发则取消（条件分支链）
**Thinking 1.00 vs No-Thinking 0.50**

**场景**：Ivan 想查订单到货时间。如果还没发货，就取消里面的净化器。如果不能部分取消，就取消整个订单并退到 gift card。如果 gift card 余额不够，就不取消了。这是一个 4 层嵌套的条件分支。

**期望动作**：0 个（最终结果应该是不执行任何修改操作）。

**No-Thinking 出错点**：DB=0.0 — 模型错误地执行了某个修改操作。当用户说"如果不能部分取消就算了"时，No-Thinking 模型没有正确遵循这个条件，可能尝试取消了整个订单。

**Thinking 为什么做对了**：正确追踪了 4 层条件，最终判断"不满足取消条件"，没有执行任何修改操作。

**错误类型**：**多层条件分支推理** — "如果 A 则 B，否则如果 C 则 D，否则不做"。No-Thinking 模型难以追踪嵌套的条件逻辑。

## 3. 错误模式分类总结

| 错误类型 | 出现的 Case | 频率 | Thinking 能避免的原因 |
|---|---|---|---|
| **多变量精确选择** | Task 20, 99 | 高 | 需要比较多个变体的价格/属性选出正确的 item_id，Thinking 在推理中逐一核对 |
| **批量操作参数构造** | Task 99, 28 | 高 | 一次 API 调用传多个 item_id，需要确保配对正确 |
| **跨订单信息传递** | Task 101, 109, 112, 71, 72 | 很高 | 从订单 A 提取地址用于订单 B，Thinking 在推理中明确追踪来源 |
| **条件分支处理** | Task 7, 57, 88 | 中 | 用户说"如果不行就..."，需要追踪嵌套条件 |
| **用户意图变更** | Task 7, 71, 72 | 中 | 确认环节用户反悔，需要回溯修正 |

## 4. 根本原因分析

### 为什么 Thinking 模型更好？

**1. 参数构造的准确性（DB 维度差距 +10.2%）**

Retail agent 的工具调用参数非常精确 — item_id 是长数字串（如 "4510078629"），payment_method_id 有特定格式（如 "credit_card_1620755"），地址有 6 个字段。No-Thinking 模型在直接生成这些参数时更容易出错，而 Thinking 模型在 `<think>` 阶段会先列出可选项、核对匹配关系，然后才输出最终参数。

**2. 多步推理的可靠性**

17 个大幅领先的 Case 中，**14 个涉及 2 个以上的操作步骤**。每增加一步操作，No-Thinking 模型的错误概率就会累积。Thinking 模型通过显式推理来维护操作计划，减少了步骤间的错误传播。

**3. 条件逻辑的追踪能力**

多个 Case 涉及"如果 A 则 B，否则 C"的条件分支。No-Thinking 模型容易在条件判断上出错（如 Task 57 的 4 层嵌套条件），或者在用户改变主意时无法回溯修正（如 Task 7, 71, 72）。

**4. 格式控制的稳定性**

No-Thinking 模型频繁泄露内部 prompt 内容（`effort: medium`、`<tool_call>` XML 标签）。这说明 SFT 训练数据中可能混入了 prompt 模板片段，No-Thinking 模型学到了这些噪声，而 Thinking 模型的 `<think>` 块提供了一个"缓冲区"，将内部推理和外部输出分离，避免了泄露。

---

## 5. 数据质量问题

在分析过程中发现 No-Thinking 模型存在以下训练数据质量问题：

1. **Prompt 泄露**：多个 Case 中出现 `effort: medium`（很可能是训练数据采集时 Claude 输出的 metadata），说明 SFT 数据清洗不够彻底。

2. **`<tool_call>` 标签泄露**：Task 101、109、112 中模型输出了 `<tool_call><arg_key>...</arg_key>` 这样的 XML 标签，这是训练数据中的 tool call 格式混入了 completion 文本。

3. **循环行为**：Task 112 中模型重复调用同一个工具多次（`get_product_details` 和 `get_order_details`），可能是训练数据中有类似的重复模式。

**建议**：检查 No-Thinking 版本的 SFT 训练数据，过滤掉包含 `effort:`、`<tool_call>`、`<arg_key>` 等标签的样本。

---

## 6. 给领导的建议

1. **Thinking 模型在 retail agent 场景中明显优于 No-Thinking 模型**，主要优势在复杂多步操作和精确参数构造上。

2. **差距的根本原因不是"更聪明"，而是"更仔细"** — Thinking 模型通过显式推理步骤来核对参数、追踪条件、维护计划，相当于人类工作中的"检查清单"。

3. **No-Thinking 模型的训练数据存在质量问题**（prompt 泄露、格式混乱），这可能贡献了部分差距。清洗数据后差距可能会缩小，但多步推理和条件分支处理的差距仍然存在。

4. **如果要进一步缩小差距**，可以：
   - 清洗 No-Thinking 训练数据中的格式污染
   - 增加更多多步操作和条件分支场景的训练样本
   - 在系统 prompt 中增加"先列出操作计划，再逐步执行"的指令，模拟部分 Thinking 效果
